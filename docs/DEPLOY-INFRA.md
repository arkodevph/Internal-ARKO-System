# Render deployment with Supabase PostgreSQL

`render.yaml` keeps the six existing Free resources during cutover. `arko-site` serves the landing page at `arkodevph.com`; `arko-internal` serves login, dashboards, finance, portal, PM, and API at `app.arkodevph.com`. Both auto-deploy after CI passes. The four other services remain available for rollback with auto-deploy off. Both active services build the same `apps/web` code with different `ARKO_SURFACE` values. Supabase remains the only database.

## Cutover

1. **Do not remove the old services until both active services work.** The Blueprint retains `arko-api`, `arko-finance`, `arko-portal`, and `arko-pm` with auto-deploy off. Review the sync preview before applying it. While any legacy service remains active, its running time still consumes the workspace's shared Free hours.
2. Verify `DATABASE_URL` and `DIRECT_URL` on `arko-internal` point to the same Supabase project, with `schema=arko`. Use Supabase's IPv4 pooler endpoints for Render. The previously shared database password was exposed; rotate it in Supabase and update the Render variables. Do not paste the new password into chat or commit it.
3. Keep `AUTH_SECRET` stable on `arko-internal`; its `AUTH_URL` and `NEXT_PUBLIC_APP_URL` are configured for `https://app.arkodevph.com`. Set `RATE_LIMIT_SECRET`, `RESEND_API_KEY`, and any S3/AI integration variables the features need. Both hourly schedulers call `arko-internal.onrender.com` so DNS cutover does not interrupt them. Set the same strong `CRON_SECRET` there and as the `ARKO_CRON_SECRET` GitHub Actions secret. Existing Blueprints might not prompt for newly added `sync: false` variables, so check them manually.
4. Back up Supabase and check Prisma migration status before applying anything. The previously observed pending migrations were `20260820000000_add_nex_send_and_reminder_permissions`, `20260926000000_pm_required_deadline_review_gate`, and `20260927120000_add_app_sessions`; the new `20260927150000_client_request_github_progress` migration adds request progress and commit updates. The PM migration sets six missing task deadlines to their creation dates, as chosen, and may make those tasks overdue. After reviewing SQL and data, run `pnpm --filter @arko/db db:deploy` manually. No migration runs during Render build.
5. Check `arko-site.onrender.com/` and `arko-internal.onrender.com/health` first. Then check public `arkodevph.com/`, `app.arkodevph.com/auth/login`, staff `/dashboard`, finance `/dashboard/finance`, client `/dashboard/client-portal`, PM `/dashboard/pm`, and both hourly workflows. Confirm staff and clients cannot access each other's protected data. The `/health` endpoint only proves the process is running; it does **not** prove database login works.

The Blueprint declares `arkodevph.com` on `arko-site` and `app.arkodevph.com` on `arko-internal`; Render still requires DNS and TLS verification. At the domain provider, replace the current root record (currently serving a Vercel 404) with Render's root-domain target for `arko-site`, and add a CNAME `app` pointing to `arko-internal.onrender.com`. Render also automatically adds `www` when a root domain is configured. Check the Blueprint sync preview for the custom-domain allowance before accepting it; do not add a payment method or paid plan. At the time of this change, `app.arkodevph.com` does not resolve, so browser login redirects will fail until DNS and certificate verification complete. The `onrender.com` URLs remain available for smoke tests. Both Free services can sleep after inactivity.

## Client request GitHub progress

An admin can attach a GitHub repository to each client request. The root `PROGRESS.md` must use Markdown checkboxes (`- [x] Done`, `- [ ] Remaining`); checklist item count determines the displayed percentage. The 10 most recent commit subjects publish on first connect, and later commits publish automatically when the hourly `.github/workflows/client-request-sync.yml` job runs. Commit bodies are never displayed. Ensure commit subjects and checklist text are safe for clients to see.

Set the same `CRON_SECRET` on `arko-internal` and `ARKO_CRON_SECRET` in GitHub Actions secrets. The sync endpoint is `POST /api/client-requests/cron` on `arko-internal`. Set `GITHUB_TOKEN` on `arko-internal` for private repositories (fine-grained Contents: Read) or to avoid unauthenticated GitHub rate limits. Do not place this token in a `NEXT_PUBLIC_` variable or in the repository URL. The scheduler wakes the free service once per hour and may delay updates until the next run.
