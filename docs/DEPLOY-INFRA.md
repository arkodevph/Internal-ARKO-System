# Render deployment with Supabase PostgreSQL

`render.yaml` declares one Free web service named `arko` for the system at `app.arkodevph.com`. Vercel deploys the public landing page at `arkodevph.com` from the same `apps/web` source. Finance, client portal, PM, and API remain routes in the one Render process. Supabase remains the only database; the Vercel deployment must not have database credentials. Do not create another Render service for the landing page.

## Cutover from the old six-service Blueprint

1. In Render, **rename the existing `arko-internal` web service to `arko` before syncing this Blueprint**. A Blueprint entry with a new name can create a new service instead of renaming the old one. Keep its service ID, Free plan, environment variables, and existing deployment. Do not deploy `render.yaml` until this rename is done and the sync preview shows an **update to that service**, not a new service. If the name `arko` is unavailable, stop and choose another name rather than creating a duplicate.
2. The workspace currently has two Render custom-domain slots occupied by old assignments, including the unverified `api.arkodevph.com`. Free an unused assignment, then attach **only** `app.arkodevph.com` to `arko`. The root domain belongs on Vercel, not Render. Review the Blueprint sync preview for any charge before accepting it; do not add a payment method or paid plan. Removing old services from `render.yaml` does **not** delete them or free their existing custom-domain assignments.
3. In the existing Vercel `arko` project, set Root Directory to `apps/web` and add `arkodevph.com` (and `www` if wanted) as the project's domains. `apps/web/vercel.json` sets the public site mode and Render API URL, then builds without running database migrations. Set `RESEND_API_KEY` for the contact form and a strong `RATE_LIMIT_SECRET` in Vercel Project Settings; remove `DATABASE_URL`, `DIRECT_URL`, `AUTH_SECRET`, and `CRON_SECRET` from that project. Vercel Hobby is restricted to non-commercial use; use an eligible plan before publishing this business landing page.
4. In Cloudflare, point the root (`@`) and optional `www` to the exact values Vercel shows for this project. Set a DNS-only CNAME for `app` targeting the renamed Render service's `onrender.com` hostname (normally `arko.onrender.com`). Remove conflicting records for those names. Verify TLS on both platforms before enabling Cloudflare proxying.
5. Verify `DATABASE_URL` and `DIRECT_URL` on `arko` point to the same Supabase project and `arko` schema. Use the Supabase IPv4 pooler from Render. The previously shared database password was exposed; rotate it in Supabase and update the Render variables. Keep `AUTH_SECRET` stable, and set `AUTH_URL` and `NEXT_PUBLIC_APP_URL` to `https://app.arkodevph.com`. Set `RATE_LIMIT_SECRET`, `RESEND_API_KEY`, and other feature secrets as needed. Blueprint `sync: false` variables on an existing service must be checked manually.
6. Back up Supabase and review pending migrations before applying anything. The previously observed pending migrations were `20260820000000_add_nex_send_and_reminder_permissions`, `20260926000000_pm_required_deadline_review_gate`, `20260927120000_add_app_sessions`, and `20260927150000_client_request_github_progress`. The PM migration sets six missing task deadlines to their creation dates. After reviewing SQL and data, run `pnpm --filter @arko/db db:deploy` manually. No migration runs during either platform's build.
7. Smoke-test `arko.onrender.com/health`, `arkodevph.com/`, `app.arkodevph.com/auth/login`, and the staff, finance, client, and PM dashboards. Confirm the Vercel preview redirects `/dashboard` to the app and returns 404 for `/api/trpc`. `/health` only proves the process is up; it does not prove database login works. Then update the three GitHub Actions scheduler URLs from the old `arko-internal.onrender.com` hostname to the new `arko.onrender.com` hostname. Only after that cutover works, suspend or delete the five old services (`arko-site`, `arko-api`, `arko-finance`, `arko-portal`, `arko-pm`) in Render. They remain intact when their Blueprint entries are removed; suspending them is a separate dashboard action.

## System keepalive

`.github/workflows/system-keepalive.yml` pings the existing service every 10 minutes on weekdays from 9:07 AM through 5:57 PM Asia/Manila. After renaming the service, change its target URL as described above. This schedule keeps the same process for both hostnames warm during working hours; it does not provide 24/7 uptime. Check Render's shared Free instance-hour use and GitHub Actions minutes. Scheduled runs may be delayed or missed, so cold starts remain possible.

## Client request GitHub progress

An admin can attach a GitHub repository to each client request. The root `PROGRESS.md` uses Markdown checkboxes (`- [x] Done`, `- [ ] Remaining`); checklist item count determines the displayed percentage. The 10 most recent commit subjects publish on first connect, and later commits publish automatically when the hourly `.github/workflows/client-request-sync.yml` job runs. Commit bodies are never displayed. Ensure commit subjects and checklist text are safe for clients to see.

Set the same `CRON_SECRET` on `arko` and `ARKO_CRON_SECRET` in GitHub Actions secrets. The sync endpoint is `POST /api/client-requests/cron` on `arko`. Set `GITHUB_TOKEN` on `arko` for private repositories (fine-grained Contents: Read) or to avoid unauthenticated GitHub rate limits. Do not place it in a `NEXT_PUBLIC_` variable or in the repository URL. The scheduler wakes the Free service once per hour and may delay updates until the next run.
