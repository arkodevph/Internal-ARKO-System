# ARKO architecture

Render runs two `apps/web` Next.js processes: `arko-site` serves the public landing page at `arkodevph.com`, and `arko-internal` serves the system at `app.arkodevph.com`. The system process handles Auth.js login at `/auth/login`, the staff/client dashboard at `/dashboard`, finance at `/dashboard/finance`, the client portal at `/dashboard/client-portal`, the PM board at `/dashboard/pm`, and the shared API at `/api/*`. Its `/` redirects to `/dashboard`. The public process redirects login and dashboard paths to the system and fetches landing content and public API features from it.

All areas use the existing ARKO users and one same-origin Auth.js session. The dashboard requires login. Client users are sent to the portal; finance requires `transactions:read`; PM rejects client and demo roles, and its tRPC router enforces staff roles and task ownership. The existing Supabase PostgreSQL database remains the only database, and `apps/web` uses Prisma directly. The API and UI are logical modules, not separate runtime services.

The `apps/api`, `apps/finance`, `apps/portal`, and `apps/pm` app shells from the previous six-service design remain in source. During cutover, their Render services remain declared with auto-deploy off for rollback; CI builds the shared web app used by both active services. The PM board component and PM tRPC router are still imported by the system process. The `AppSession` API routes remain for compatibility but are not used by the unified login.

Free Render services share an instance-hour allowance and spin down after inactivity. Two active services use more hours than one; the legacy services also consume hours whenever active. The historic Vite/Django/Neon documents under `docs/superpowers` are planning records, not current deployment instructions.
